# JudgeBox 更新报告

发布日期：2026-11-12

版本号v1.3.1(2026.11.12)

## 一、这次更新解决了什么

1. **对拍时参考程序也能当编辑器写**
   以前的对拍的时候用的程序栏是纯文本编辑界面，不方便现场手写代码，于是更新。

   - 随机对拍里的参考程序和待测程序使用同一套编辑器。
   - 两边各自选择语言，都有高亮、行号、括号匹配，以及 VS Code / Vim 键位。
   - 参考程序在对拍模式下停顿后做语法检查，结果显示在参考程序自己的状态行。
   - 生成数据、分别运行、比较输出的流程没有改。提交时仍然读取两个文本框里的源码。
2. **开发启动不再固定跑旧程序**
   对于开发版，根目录中的启动JudgeBox的cmd 原先的启动逻辑是**只要根目录有JudgeBox.exe**，就启动，否则去/build下找exe，但是这样会导致我们改完某一段代码 想要启动本地预览时，启动的却是旧的exe，即使编译过也是旧的 何况有时候忘了CMake --build build,所以这次主要更新了启动的cmd的逻辑，如下

   - `启动JudgeBox.cmd` 会先执行 `cmake --build build`。这是增量编译：没改过的文件不会重编。
   - 编译完成后，在项目根目录和 `build` 目录的 `JudgeBox.exe` 里启动修改时间较新的一份。
   - 如果本仓库里已经有 JudgeBox 在运行，脚本会先关掉它，避免单实例锁把旧窗口留在前面。
   - 因为测试的时候，发现启动编译一次要较长时间，所以使用并行编译参数来提高启动速度，而且默认增量编译 这样以后的速度会快一些，并行路数通过读取 Windows 的逻辑处理器数量，再用内存封顶：总内存 GB 的向下取整值 减去 2，和逻辑处理器数取较小值。比如作者的这台 8 核 16 线程、约 16 GB（实际15.7GB） 内存的机器得到 `-j 13`。

## 二、使用方式

改完 `src`、`CMakeLists.txt` 或已打包的页面后，双击 `启动JudgeBox.cmd` 即可。页面源码在 `web\editor\main.js` 时，需要先在仓库根目录执行 `npm run build:editor`，生成新的 `web\editor.js`，启动脚本才会把它编进程序。

要跑测试、复制根目录程序并打包，仍然使用 `build.ps1`。启动脚本不跑测试。

## 三、实测

在 i7-11800H 上，从空的编译结果完整重编：

| 并行      | 耗时    | 编译进程峰值 |
| --------- | ------- | ------------ |
| 不并行    | 61.0 秒 | 0.7 GB       |
| `-j 4`  | 39.2 秒 | 2.3 GB       |
| `-j 13` | 32.1 秒 | 2.8 GB       |
| `-j 16` | 31.3 秒 | 2.8 GB       |

什么都没改时，`cmake --build build` 核对依赖大约 0.5 秒。这次核对只看构建系统记录的源码、头文件、四个前端文件和编译器自带头文件，不会扫描工具链，这是增量编译本身的好处。

## 四、已知行为

- 启动脚本仍会在启动前清空项目里的 `runs` 目录。
- 界面编在 exe 里。只保存了 `web` 下的源文件、还没执行 `cmake --build` 时，正在运行的程序不会变。
- 内存封顶是脚本里的估算。这次完整编译的峰值约 2.8 GB，`-j 13` 和 `-j 16` 的耗时差别在一次测量的误差内。
